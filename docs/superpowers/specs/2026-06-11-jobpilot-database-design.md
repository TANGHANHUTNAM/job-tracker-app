# JobPilot Database Design

## Summary

This design uses `Supabase Auth + Prisma + Supabase PostgreSQL`.

- `auth.users` is the source of truth for authentication
- `profiles` is the app-level user table
- `profiles.id` matches `auth.users.id`
- authorization is based on `role` and `isBlocked`
- MVP business tables are `job_sources`, `job_applications`, and `reminders`

Chosen decisions:

- Auth model: `Supabase Auth + profiles`
- Profile creation: app-side insert after signup (`Option A`)
- Roles: `ADMIN`, `USER`
- Blocking model: soft block with `isBlocked`
- Admin scope: manage app users from a dedicated admin page

## Goals

- Keep authentication simple and aligned with Supabase
- Keep business data isolated from auth internals
- Support user-scoped job tracking for regular users
- Support admin user management in MVP
- Leave room for future audit logging without major schema changes

## Non-Goals

- No hard-disable at the Supabase Auth provider level in MVP
- No admin audit/history tables in MVP
- No contacts, resumes, or resume-job mapping in MVP
- No multi-tenant organization model

## Access Model

### Regular user

- Can sign up and sign in through Supabase Auth
- Can only read and mutate their own jobs and reminders
- Cannot access admin pages

### Admin user

- Can access a user-management page
- Can view all app users
- Can create new profile records only in flows that are tied to a valid auth user
- Can block or unblock users by toggling `isBlocked`

### Blocked user

- Still exists in `auth.users` and `profiles`
- Keeps all jobs and reminders
- Cannot use the application after app-side checks run

### `profiles`

Purpose:

- Stores app-level identity and authorization data
- Mirrors authenticated users from `auth.users`

Fields:

```prisma
model Profile {
  id         String   @id
  email      String   @unique
  fullName   String?
  avatarUrl  String?
  role       AppRole  @default(USER)
  isBlocked  Boolean  @default(false)
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  jobs       JobApplication[]
  reminders  Reminder[]

  @@map("profiles")
  @@index([role])
  @@index([isBlocked])
}
```

Notes:

- `id` is not generated by Prisma. The app writes the same UUID returned by Supabase Auth.
- `email` is duplicated here for admin queries and app display.

### `job_sources`

Purpose:

- Stores admin-managed job application sources
- Supports default seed data and future source expansion without schema changes

Fields:

```prisma
model JobSource {
  id          String           @id @default(cuid())
  name        String           @unique
  slug        String           @unique
  description String?
  isActive    Boolean          @default(true)
  sortOrder   Int              @default(0)
  createdAt   DateTime         @default(now())
  updatedAt   DateTime         @updatedAt

  jobs        JobApplication[]

  @@map("job_sources")
  @@index([isActive, sortOrder])
}
```

Notes:

- Admin manages this table.
- `isActive = false` hides the source from new selections but preserves old job history.
- `slug` is the stable unique key for seed upserts.

### `job_applications`

Purpose:

- Core entity for job tracking
- Owned by one profile

Fields:

```prisma
model JobApplication {
  id          String    @id @default(cuid())
  userId      String

  companyName String
  jobTitle    String
  jobUrl      String?
  location    String?
  salaryRange String?
  jobType     JobType?
  sourceId    String?
  status      JobStatus @default(SAVED)

  appliedDate DateTime?
  deadline    DateTime?
  description String?
  notes       String?

  createdAt   DateTime  @default(now())
  updatedAt   DateTime  @updatedAt

  user        Profile   @relation(fields: [userId], references: [id], onDelete: Cascade)
  source      JobSource? @relation(fields: [sourceId], references: [id], onDelete: SetNull)
  reminders   Reminder[]

  @@map("job_applications")
  @@index([userId, createdAt])
  @@index([userId, status])
  @@index([userId, sourceId])
  @@index([userId, jobType])
  @@index([companyName])
  @@index([jobTitle])
}
```

Notes:

- `status` drives Kanban columns and analytics.
- `companyName` and `jobTitle` stay as strings for MVP simplicity.
- `salaryRange` stays as string in MVP to avoid premature salary normalization.
- `sourceId` is nullable so old data remains valid even if a source is later removed manually.

### `reminders`

Purpose:

- Tracks follow-ups, interviews, deadlines, and custom reminders

Fields:

```prisma
model Reminder {
  id               String       @id @default(cuid())
  userId           String
  jobApplicationId String?

  title            String
  reminderDate     DateTime
  type             ReminderType @default(CUSTOM)
  isCompleted      Boolean      @default(false)

  createdAt        DateTime     @default(now())
  updatedAt        DateTime     @updatedAt

  user             Profile      @relation(fields: [userId], references: [id], onDelete: Cascade)
  jobApplication   JobApplication? @relation(fields: [jobApplicationId], references: [id], onDelete: Cascade)

  @@map("reminders")
  @@index([userId, reminderDate])
  @@index([userId, isCompleted])
  @@index([jobApplicationId])
}
```

Notes:

- Keeping both `userId` and `jobApplicationId` simplifies ownership checks and reminder list queries.
- `jobApplicationId` is nullable so the model can support standalone reminders later without redesign.

## Relationship Summary

- `profiles 1:n job_applications`
- `job_sources 1:n job_applications`
- `profiles 1:n reminders`
- `job_applications 1:n reminders`

## Query Rules

### User-scoped reads and writes

Every user-facing query must filter by authenticated profile id.

Example:

```ts
const jobs = await prisma.jobApplication.findMany({
  where: {
    userId: currentUser.id,
  },
  orderBy: {
    createdAt: 'desc',
  },
});
```

### Block checks

After resolving the authenticated user, the app must read `profiles.isBlocked`.

- If `true`, deny access to app pages and mutations
- If `false`, continue normally

### Admin checks

Admin routes require:

- authenticated session
- matching `profiles.role === ADMIN`
- `profiles.isBlocked === false`

## Signup and Profile Creation Flow

Chosen flow: `Option A`, app-side profile creation.

Sequence:

1. User signs up with Supabase Auth
2. Supabase returns authenticated user id and email
3. App inserts a row into `profiles`
4. Default role is `USER`
5. Default `isBlocked` is `false`
6. User is redirected into the app

Failure handling:

- If auth succeeds but profile insert fails, the app should show a recoverable error and log the failure
- The app should not silently continue without a `profiles` row
- On sign-in, if a valid auth session exists but no profile is found, redirect to a recovery path or create the profile if the policy allows it

## Admin User Management Scope

The MVP admin page can support:

- list users from `profiles`
- search by email or name
- view role and blocked status
- block or unblock users

Out of scope for MVP:

- role history
- impersonation
- hard deletion from auth system
- bulk actions

## Prisma Datasource Notes

Current datasource is PostgreSQL, which matches Supabase.

Recommended datasource block:

```prisma
datasource db {
  provider = "postgresql"
}
```

Notes:

- Connection URLs live in `prisma.config.ts`, not `schema.prisma`
- `DATABASE_URL` can use Supabase pooled connection
- `DIRECT_URL` is used as the shadow database connection for migrations where applicable

## Database Initialization Guide

### 1. Create Supabase project

- Create a new Supabase project
- Save the project URL and keys
- Open the database settings and copy the Postgres connection strings

### 2. Configure environment variables

Minimum expected values:

```env
DATABASE_URL="postgresql://..."
DIRECT_URL="postgresql://..."
NEXT_PUBLIC_SUPABASE_URL="https://<project>.supabase.co"
NEXT_PUBLIC_SUPABASE_ANON_KEY="<anon-key>"
SUPABASE_SERVICE_ROLE_KEY="<service-role-key>"
```

### 3. Update Prisma schema

- Add the datasource URLs
- Add enums and the three MVP models
- Keep table names mapped with `@@map(...)` for clean SQL naming

### 4. Generate migration

Recommended commands:

```bash
npx prisma migrate dev --name init_auth_profiles_jobs_reminders
npx prisma generate
```

### 5. Seed default job sources

Recommended command:

```bash
npm run db:seed
```

Default sources should be inserted with upsert behavior so reseeding is safe.

### 6. Create first admin account

Suggested sequence:

1. Create the account through Supabase Auth
2. Insert matching row into `profiles`
3. Set `role = ADMIN`

This can be done by a seed script or a one-time admin bootstrap script.

### 7. Seed baseline data

Recommended initial seed:

- default job sources
- one admin profile
- optional one demo user
- optional demo jobs and reminders for local development

### 8. Enforce app-side guards

At minimum, add these checks:

- route protection for authenticated pages
- admin-only protection for `/admin/users`
- blocked-user denial after profile lookup
- ownership filters on every user data query

## Future Expansion

The schema is intentionally ready for later additions:

- `contacts`
- `resume_versions`
- `job_resumes`
- `admin_action_logs`
- `saved_filters`
- `activity_timeline`

These can be added without changing the current ownership model.
